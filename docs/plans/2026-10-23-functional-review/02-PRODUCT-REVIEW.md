# 全项目功能与使用流程调研报告（非额度主链路 · 修订版）

## 1. 基线与证据范围

本报告基线为已安装/已发布的版本 **0.1.8**（代码提交 `23edaf1`，产品标签 `v0.1.8`）以及当前工作树最新改动（HEAD=`92751ab`）。本报告遵循与额度审查（`docs/plans/2026-10-23-functional-review/01-QUOTA-REVIEW.md`）分工原则，**专注非额度主链路的全项目产品功能、使用流程与人机交互闭环**。

调研范围严格覆盖项目九大功能维度：
1. **新用户安装/运行依赖和首次接入**
2. **添加/备份/切换/恢复/重命名删除/浏览器联动**
3. **独立浏览器状态/登录隔离及资料生命周期**
4. **快速配置与故障修复**
5. **用量统计与归属/时区/导出**（侧重使用体验、时区展示、导出与兜底账号绑定）
6. **网络连通性与 CLI 维护**
7. **电脑设置与恢复**
8. **设置/帮助/命令面板/手工交接**
9. **本地数据备份导出/迁移/恢复与版本交付**

本审查通过 `rg` 与源码逆向追踪实现链路（从前端 React/TypeScript 组件、Cromma UI 原语，到 Tauri IPC 命令、Rust 原生模块、PowerShell 脚本）。严格规避对真实 `.local`、`appdata`、`identity-vault` 真实账号、`.env`、`credentials.*`、`credentials.rs` 的探测，不启动真实浏览器，不结束任何 `claude.exe` 进程，不改动用户宿主系统设置。所有源码引用均采用仓库可移植相对路径与行号。

## 2. 功能全景评估与推荐前 5 项

当前 Claude-Local 在本地安全防护、进程隔离、加密身份暂存/恢复（BAGAID01）、原生窗口状态记忆以及 IANA 真实夏令时日历对齐等方面具备了扎实的工程底座。0.1.7 引入的 6 项生产力改进（Ctrl+K、TSV 导出、诊断复制、手填交接、搜索排序、CLI 读取恢复）与 0.1.8 的侧栏自适应及窗口外框恢复均已稳定落地。

经 Astra 专项复核并校准后，全项目在人机交互闭环、工作流打断防护、多账号用量归属契约、系统基线保护与跨机安全迁移等关键场景中，提炼出前 5 项重点提升建议。

### 核心推荐前 5 项（Top 5 Priorities）

1. **[P-01] CLI 未安装状态下缺少首次安装引导与命令一键复制路径（必修 · 工作量 S · 独立无依赖）**
   - **核心痛点**：首次接入流程断裂。未安装状态下禁用“检查更新”与“一键更新”是合理的保护性逻辑，但界面缺乏明确的首次安装指引与官方命令（如 `npm install -g @anthropic-ai/claude-code` 或 Windows 官方脚本命令）的复制入口，导致新用户卡在接入流程。
2. **[P-02] 身份切换在联动开启时默认启动浏览器构成工作流打断，建议改为可选启动行为（必修 · 工作量 S · 独立无依赖）**
   - **核心痛点**：显式切换身份已有关闭/重开浏览器的确认，但联动开启时，原先关闭的浏览器仍会被启动。对只使用CLI的流程，这可能是不必要的打断；建议保留切换前运行状态，或提供明确启动偏好。实际焦点和窗口大小未在本轮验证。
3. **[P-03] 用量统计缺少基于稳定账号 ID（Fallback Account ID）的显式绑定命令与前端入口（高收益 · 工作量 M · 独立无依赖）**
   - **核心痛点**：前后端契约未闭环。原生层依赖 `fallback_name` 且必须恰好命中单个候选才写入 meta；在没有名称输入或多账号场景下后端不会自动种植 meta。应改为由前端提供显式的稳定账号 ID 下拉选择器与专属 IPC 指令，按稳定 ID 而非可变名称持久化绑定。
4. **[P-04] “对齐美国系统环境”破坏性修改电脑配置后缺失原始基线快照与一键恢复（高收益 · 工作量 M · 独立无依赖）**
   - **核心痛点**：宿主系统安全护栏缺失。点击对齐美国环境会直接修改宿主 Windows 的时区与系统语言，但系统从未备份首次运行前的系统配置，用户完成网页验证后无法一键恢复自己的中文/原始时区。
5. **[P-05] 身份保险库跨机迁移、口令保护安全备份与数据目录定位（高收益 · 工作量 M · 独立无依赖）**
   - **核心痛点**：设置页缺少完整的备份/恢复及目录定位流程。包含 `key.bin` 的普通归档没有独立口令保护，若备份落入他人手中会暴露主密钥；这不是已经发生泄漏的证据。应增加用户口令认证外层封装，保持源数据不删、导入至新私有目标并校验一致性。

## 3. 详细改进建议清单

### P-01 — CLI 未安装状态下缺少首次安装引导与命令一键复制路径

- **来源文件行号**：
  - 前端保护性禁用逻辑：`src/claude-cli-panel.tsx:80-96`
  - 原生未安装状态阻断：`src-tauri/src/claude_cli.rs:242, 252`
- **现状**：
  当用户初次安装 Claude-Local 且本地尚未安装 Claude Code CLI 时，`claude_cli_read` 返回 `status.method = ""`。面板渲染为“未安装”灰色胶囊，右侧操作按钮保持保护性禁用：
  `disabled={blocked || loading || !!action || !!readError || !status?.method}`。
  原生 `claude_cli_check` 与 `claude_cli_manage` 内部直接返回 `Err("cli.error.notInstalled")`。
- **具体触发与用户后果**：
  新用户在引导第 3 步看到“在终端运行 claude 完成授权”，回到身份面板看到 CLI“未安装”。由于未安装时禁用更新和检查属于合理保护，但面板未提供首次安装向导或安装命令复制入口，新用户缺少直观的下一步操作指引。
- **已实现 vs 真缺口**：
  - 已实现：CLI 状态读取重试、运行中状态互斥保护、版本比较。
  - 真缺口：**缺少首次接入引导与官方安装命令一键复制路径**。
- **建议范围**：
  1. 在 `src/claude-cli-panel.tsx` 中，当 `!status?.method` 时，将主操作按钮切换为“复制安装命令”；
  2. 复制内容提供平台官方推荐命令：Windows 下提供 `irm https://claude.ai/install.ps1 | iex` 或 `npm install -g @anthropic-ai/claude-code`，并给出轻量复制反馈；
  3. 在面板说明中清晰告知用户“在系统终端中粘贴执行上述命令完成安装后，点击此处刷新即可识别”。
- **依赖与安全边界**：
  不自动静默执行后台外部脚本安装，采用**一键复制官方命令 + 用户主动终端执行**，符合不静默修改宿主开发环境的安全边界。
- **验收标准**：
  在无 CLI 的模拟环境下，面板显示“未安装”；主操作按钮变为“复制安装命令”；点击后剪贴板获得经校验的合法安装命令并展示复制成功提示；外部安装完成后点击刷新能正确识别版本。
- **优先级 / 工作量 / 额度依赖**：必修 | 工作量 S | 独立无依赖
- **问题属性**：合理优化（闭环新手首次接入路径）

### P-02 — 身份切换在联动开启时默认启动浏览器构成工作流打断，建议改为可选启动行为

- **来源文件行号**：
  - 原生联动重开逻辑：`src-tauri/src/browser/workspaces.rs:160-163`
  - 联动开关与调用入口：`src-tauri/src/identities/mod.rs:244-249`
- **现状**：
  在 `workspaces::transition` 函数中，当身份切换完成时，执行如下恢复逻辑：
  ```rust
  if (result.is_ok() && database(&root)?.browser_link()?.enabled) || was_running {
      launch_locked(app, reporter)?;
  }
  ```
  只要用户启用了浏览器联动（`browser_link.enabled == true`），无论切换前浏览器是否正在运行（即使 `was_running == false`），都会无条件调用 `launch_locked(app, reporter)` 启动 Chromium 伴生浏览器。
- **具体触发与用户后果**：
  用户显式切换身份属于主动操作，与普通冷启动不同。资料联动确保绑定与种子隔离，但原先关闭的浏览器也会在切换后启动。该额外启动对CLI使用者可能没有帮助；源码能确认启动行为，本轮未验证实际焦点和全屏状态。
- **已实现 vs 真缺口**：
  - 已实现：浏览器多槽位隔离（`contexts/{slot}`）、独立种子隔离、优雅退出（`WM_CLOSE` / `rf_browser_quit`）。
  - 真缺口：**显式切号时的启动行为缺乏对切换前运行状态的尊重或显式用户偏好**。
- **建议范围**：
  修改 `src-tauri/src/browser/workspaces.rs:160` 的条件判定：仅当切换前浏览器本身处于运行中状态（`was_running == true`），切换后才自动重开新身份绑定的浏览器；若切换前浏览器未运行，仅执行 `refresh_launch_args(app)?` 同步底层启动参数与资料槽位，不自动拉起浏览器；亦可在浏览器高级设置中增加“切号时自动打开浏览器”的可选开关。
- **依赖与安全边界**：
  不改动资料槽位隔离、不修改种子计算，保持切换后启动参数实时对齐，仅消除非预期的自动前台弹窗打断。
- **验收标准**：
  合成测试覆盖两种场景：在伴生浏览器关闭状态下切号，验证新槽位参数已更新但未拉起 `chrome.exe`；在伴生浏览器打开状态下切号，验证旧浏览器退出后新身份浏览器正常重新启动。
- **优先级 / 工作量 / 额度依赖**：必修 | 工作量 S | 独立无依赖
- **问题属性**：合理优化（提升工作流连续性）

### P-03 — 用量统计缺少基于稳定账号 ID（Fallback Account ID）的显式绑定命令与前端入口

- **来源文件行号**：
  - 前端统计调用缺少入参：`src/usage-statistics.tsx:64`
  - 原生命令签名接收 fallback_name：`src-tauri/src/identities/usage.rs:1028-1030`
  - 原生按名称筛选及 meta 写入条件：`src-tauri/src/identities/usage.rs:1269-1298`
  - 产品设计文档约束：`docs/USAGE_STATISTICS.md:46-55`
- **现状**：
  原生 `usage.rs` 中，当且仅当传入 `fallback_name` 且在 `account_map` 中恰好过滤匹配到唯一候选账号时（`candidates.len() == 1`），才会执行 `INSERT OR IGNORE INTO meta(key,value) VALUES('fallback_account_id', ?1)`。如果调用方未传入 `fallback_name`，`candidates` 为空，后端**绝不会**自动种植 meta。
  同时，前端 `src/usage-statistics.tsx` 在调用 `usage_statistics_read` 时从未传递此参数，页面上也无任何设置控件；此外，依赖可变显示名称（name）而非稳定账号 ID（id）进行绑定存在重命名脱钩风险。
- **具体触发与用户后果**：
  用户拥有多个账号时，因早期会话缺少 HMAC 归属，部分历史 Token 长期只能归入“未归属历史”。多账号用户无法在界面上指定某个主力账号来吸收未归属历史，导致用量统计契约在前端未闭环。
- **已实现 vs 真缺口**：
  - 已实现：后端 `usage.sqlite` 中 `meta.fallback_account_id` 键读取与按 ID 聚合吸收逻辑。
  - 真缺口：**缺少显式按稳定账号 ID（而非易变名称）设置兜底账号的原生写入指令，且前端无交互设置入口**。
- **建议范围**：
  1. 新增原生命令 `usage_set_fallback_account(account_id: Option<String>)`，直接将经校验合法的稳定账号 ID 写入 `usage.sqlite` 的 `meta` 表（或清空取消兜底）；
  2. `usage_statistics_read` 直接读取数据库已保存的 `fallback_account_id`，废弃易产生歧义的 `fallback_name` 临时匹配逻辑；
  3. 在用量分析筛选栏下方或软件设置中提供“未归属历史兜底账号”下拉选择器。
- **依赖与安全边界**：
  仅按稳定目录 ID 聚合未归属记录，不改写原始 JSONL 与数据库原始事件的真实归属，保证事件级审计证据的不可篡改性。
- **验收标准**：
  通过原生命令设置指定账号 ID 为兜底账号，验证刷新后未归属历史 Token 正确合并到该账号的 totals 与 daily 序列中；账号重命名后兜底绑定不失效；设为 None 时未归属用量恢复独立。
- **优先级 / 工作量 / 额度依赖**：高收益 | 工作量 M | 独立无依赖
- **问题属性**：确认缺口（前后端绑定契约待闭环与加固）

### P-04 — “对齐美国系统环境”破坏性修改电脑配置后缺失原始基线快照与一键恢复

- **来源文件行号**：
  - 浏览器对齐机器实现：`src-tauri/src/browser/mod.rs:709-738`
  - 电脑环境设置交互：`src/system.tsx:1-120`
  - Windows 原生系统时区/语言修改：`src-tauri/src/windows.rs:748-845`
- **现状**：
  当用户在浏览器页点击“对齐美国系统环境”时，系统调用 `rf_system_timezone`（执行 `tzutil /s`）将 Windows 时区修改为美国出口时区，并调用 `windows-region.ps1` 将系统首选语言更改为 `en-US`。但是，系统**从未在执行修改前保存机器原始的系统时区与语言基线**，电脑环境页也没有“恢复本机原始设置”的功能。
- **具体触发与用户后果**：
  用户使用该功能完成 Claude 网页端注册或风控排查后，日常需要切回中文及本地时区（如 `China Standard Time` / `zh-CN`）。由于应用没有记录原始基线，用户必须手动去 Windows 复杂的多层“设置 - 时间和语言”中重新寻找并手动恢复，极易因选错区域或时区造成日常办公日历混乱。
- **已实现 vs 真缺口**：
  - 已实现：原生 `system_read` 读取当前时区与语言、受控原生设置调用、设置失败打开 Windows 设置面板。
  - 真缺口：**缺少首次修改前的环境基线持久化存档（如 `system-baseline.json`）与一键还原入口**。
- **建议范围**：
  1. 在首次调用 `rf_system_timezone` 或 `rf_system_region` 修改系统前，原生层自动将当前的 `system_read()` 完整快照原子写入私有 `system-baseline.json`；
  2. 在“电脑环境”页面顶部增加“恢复本机初始环境（时区与语言）”按钮；
  3. 点击恢复时，先进行二次确认并列出将要恢复的原始时区与语言名称，确认后按基线数据原样调回。
- **依赖与安全边界**：
  基线文件保存在应用 AppData 目录，不读取敏感硬件信息；调用仍沿用现有的 `tzutil` 和 `windows-region.ps1`，无需提升额外权限。
- **验收标准**：
  在初始机器环境下点击对齐美国环境，验证时区与语言成功改变且生成基线文件；点击“恢复本机初始环境”并确认，验证系统时区恢复为原时区、首选语言恢复为原语言，核验通过后界面状态恢复正常。
- **优先级 / 工作量 / 额度依赖**：高收益 | 工作量 M | 独立无依赖
- **问题属性**：合理优化（高价值安全护栏）

### P-05 — 身份保险库跨机迁移、口令保护安全备份与数据目录定位

- **来源文件行号**：
  - 设置页静态路径展示：`src/settings.tsx:100-135`
  - 保险库物理结构与密钥依赖：`src-tauri/src/identities/store.rs:40-75`
  - 数据库与归档操作：`src-tauri/src/identities/database.rs:1-100`
- **现状**：
  用户的所有加密身份均存储在 `%APPDATA%\ai.local.claude-local\identity-vault` 中，其核心依赖 `key.bin`（32 字节随机主密钥）进行 AES 加解密。但在整个前端 UI 中（包括“软件设置”的“独立资料与保险库目录”），仅用静态文本显示了该路径。用户既无法点击按钮直接在资源管理器中定位目录，也缺乏受控的跨机备份迁移方案。
- **具体触发与用户后果**：
  用户更换新电脑或重装系统时，若手动复制，普通未加密归档打包包含 `key.bin` 会导致静态主密钥明文暴露；若漏拷 `key.bin`，所有 `.baga` 归档将永久报废。
- **已实现 vs 真缺口**：
  - 已实现：单身份 `.baga` 归档、SQLite 记录版本管理、HMAC 校验、残留安全删除。
  - 真缺口：**缺乏用户口令派生加密的外层安全备份包、源文件不破坏迁移流程、以及受控的原生数据目录定位能力**。
- **建议范围**：
  1. 在软件设置的“独立资料与保险库目录”卡片增加“在文件夹中定位”按钮（调用 Windows Shell 定位确切的 AppData 根目录，路径硬编码自 `app.path().app_data_dir()`，拒绝外部路径输入）；
  2. 增加“加密导出保险库备份”功能：在持有 Cleaner 锁时，将 `identity-vault` 数据通过**用户输入的独立口令**派生外层密钥（如 Argon2id + AES-GCM）打包导出为单个安全归档，**严禁明文导出包含 key.bin 的未加密压缩包**；
  3. 增加“导入保险库备份”流程：导入时不删除源文件，先复制解密到新的私有临时目标，验证签名（BAGAID01）、哈希、SQLite 版本及身份计数一致性，用户确认后再并入本地。
- **依赖与安全边界**：
  严格保持原有 `BAGAID01`、SQLite `user_version=3` 内部格式不变；源目录绝不破坏性删除；导出文件完全留在本地由用户掌控，绝不上云。
- **验收标准**：
  执行口令加密导出，生成的备份包无法在没有口令的情况下解开；在干净的新环境下输入正确口令导入，数据完整性核验通过后，所有已保存身份与关联状态完整恢复。
- **优先级 / 工作量 / 额度依赖**：高收益 | 工作量 M | 独立无依赖
- **问题属性**：合理优化（生命周期关键能力，合并数据目录定位）

### P-06 — 快速配置页缺乏向“文件残留清理”深层维护功能的导流

- **来源文件行号**：
  - 快速配置六大导流卡片：`src/quick-actions.tsx:50-80`
  - 残留面板内嵌在身份页最下端：`src/identities.tsx:1069`
  - 残留扫描逻辑：`src/claude-residue-panel.tsx:35-80`
- **现状**：
  `QuickSetupPanel` 提供了浏览、电脑、网络、身份、用量、设置六个导流卡片，定位为“快速配置与环境总览”。而强大的“Claude 文件残留清理”（`ClaudeResiduePanel`，负责白名单缓存清理与排障重置）却被折叠放置在“身份管理”长列表的最底部（在身份卡网格与 CLI 卡片之下）。新用户或遭遇配置冲突的用户在快速配置页完全看不到这一排障功能。
- **具体触发与用户后果**：
  当用户遇到 Claude 登录状态错乱、缓存过大或配置冲突时，按照直觉进入“快速配置”寻求排障指引，但页面只引导去“电脑环境”或“网络环境”，用户根本无法发现应用底层已经具备完善的安全残留清理工具。
- **已实现 vs 真缺口**：
  - 已实现：白名单残留扫描、风险等级过滤（safe/login/history）、事务安全清理与复查。
  - 真缺口：**功能可见性与排障导流断层**。
- **建议范围**：
  在快速配置页的推荐卡片中，增加“系统与缓存排障”卡片，点击可直接跳转至身份管理页并平滑滚动到“文件残留”面板，提升高频排障能力的可触达性。
- **依赖与安全边界**：
  仅做交互定位和导航跳转，不改变底层残留白名单或清理执行逻辑。
- **验收标准**：
  在快速配置页点击排障卡片，应用切换至身份管理页并聚焦于“Claude 文件残留”面板，且不触发非预期的清理动作。
- **优先级 / 工作量 / 额度依赖**：可选 | 工作量 S | 独立无依赖
- **问题属性**：合理优化

### P-07 — 身份切换事务异常时的只读诊断、救援副本与安全恢复通道

- **来源文件行号**：
  - 恢复状态锁定全部操作：`src-tauri/src/identities/store.rs:50, 480, 520, 680`
  - 恢复执行流程：`src-tauri/src/identities/store.rs:750-850`
- **现状**：
  在 `Store::open` 或任何事务开始时，只要 `self.db.get("recovery")` 返回 `Some(id)`，整个系统进入锁定保护模式，除了 `identities_switch(recover: true)` 之外的所有操作（保存、切换、删除、重命名）均被阻断。如果由于外部意外（如磁盘损坏、权限异常），导致 `store.recover()` 在执行中反复失败，用户界面将停留在“请先恢复未完成的身份切换”。
- **具体触发与用户后果**：
  极罕见的极端写损坏情况下，常规恢复若无法成功，用户需要安全排查手段。此时绝对不能通过破坏性清场来强行解除锁定（违反仓库保留证据与不可逆操作红线）。
- **已实现 vs 真缺口**：
  - 已实现：两阶段提交保护、断电恢复检查点暂存。
  - 真缺口：**连续恢复失败时，缺少只读诊断导出与安全的救援副本落盘机制**。
- **建议范围**：
  1. 坚决移除任何“强行清空 recovery / 强行切到空身份”的破坏性方案，严禁丢弃未完成事务证据；
  2. 增加只读诊断能力：当恢复失败时，提供“导出故障诊断包”，记录失败原因、文件校验结果与事务状态日志；
  3. 增加救援副本生成：经用户明确操作，将本产品范围内的相关暂存资料复制到全新私有救援目标，例如产品AppData下的新目录；校验所有权、权限、完整性并保留源现场。不把产品运行救援放进源码仓库，也不扫描或复制任意目录；
  4. 支持在新私有目标上进行安全测试恢复，原现场与 SQLite 原始记录保持完整冻结，直至人工核实。
- **依赖与安全边界**：
  严禁删除、覆盖或清空已有证据；符合全局高危命令与工作区数据保留红线。
- **验收标准**：
  注入模拟损坏后，常规恢复失败时系统输出清晰的只读诊断日志，并生成完整镜像救援副本，原数据库与恢复标记未受任何破坏性清除。
- **优先级 / 工作量 / 额度依赖**：可选 | 工作量 S | 独立无依赖
- **问题属性**：合理优化（只读诊断与非破坏性容灾）

### P-08 — 浏览器全清理操作仅独立标记网页会话状态未知，不影响 CLI 授权与额度摘要

- **来源文件行号**：
  - 浏览器全清理调用：`src/browser.tsx:110-125`
  - 原生清理与资料重置：`src-tauri/src/browser/mod.rs:560-610`
- **现状**：
  在“浏览环境”页面中执行“深度重置当前浏览器（全清理）”后，原生层重置了当前绑定身份的 Chromium `user-data-dir`（清空了网页端 Cookie 与缓存）。此时身份管理页的当前工牌显示的网页登录态未即时刷新；但必须明确区分：**网页端 Cookie 清理绝不代表 CLI 授权失效，也不代表本地可信历史额度失效**。
- **具体触发与用户后果**：
  部分交互状态需要及时响应，但不能混淆来源。Windows CLI 的授权材料由 CLI 自身凭据存储维护，`.claude.json` 中的账号配置和缓存不等于凭据正文；额度账本由 Python 维护。浏览器全清理会影响相应网页登录会话，不代表 CLI 授权或可信历史观测失效。
- **已实现 vs 真缺口**：
  - 已实现：资料底层清理干净、退出保障、CLI 凭据与浏览器存储严格物理分离。
  - 真缺口：**全清理后的状态反馈需精准对齐：仅将网页登录状态标记为“未知/需重新登录”，严禁误清 CLI 授权与额度摘要**。
- **建议范围**：
  先明确网页登录状态的真实观测来源及接口；目前不能把拟议字段 `current.web.login_status` 当作已有能力。若后续增加该状态，应在 `browser_clear` 成功后仅将其置为未知或需重新连接，并重新核验。现有会话轮换及回到身份页时的重读机制应复用，工牌上的5h/7d历史观测与CLI授权保持独立。
- **依赖与安全边界**：
  严格保持浏览器资料与 CLI 存储的物理与逻辑隔离界限。
- **验收标准**：
  合成测试验证清理后会话失效与重读行为；只有实现可信网页登录状态来源后才验收其未知/待连接提示。CLI授权和已有5h/7d观测保持独立，不能要求其随网页清理而变成未登录或零额度。
- **优先级 / 工作量 / 额度依赖**：可选 | 工作量 S | 独立无依赖
- **问题属性**：合理优化（精准解耦各子系统状态反馈）

### P-09 — 用量统计界面缺少活动 IANA 时区与夏令时区间的直观标识

- **来源文件行号**：
  - 前端工具栏渲染：`src/usage-statistics.tsx:120-150`
  - TSV 导出已支持时区：`src/usage-export.ts:1-60`
- **现状**：
  0.1.7 版本成功在原生层实现了基于 IANA 时区（如 `America/New_York`）的真实日历边界计算与 23/24/25 小时夏令时日对齐，且 TSV 导出已完整记录该时区。然而在前端“用量分析”页面的界面呈现上，工具栏仅显示了日期跨度（如“2026年10月23日”），卡片头部没有任何时区标识。
- **具体触发与用户后果**：
  跨时区工作的用户在查看“今天”的每小时分布时，如果无法直观确认当前图表是以本机时区还是目标时区统计，容易产生小时槽位理解偏差。
- **已实现 vs 真缺口**：
  - 已实现：后端精确计算、时区传递、TSV 导出时区标记。
  - 真缺口：**界面视图上的轻量时区徽标展示缺失**。
- **建议范围**：
  在用量分析工具栏的日期范围旁，增加紧凑的时区胶囊（例如：`America/New_York (EDT)` 或 `Asia/Shanghai (CST)`）；在夏令时切换日（23h/25h）额外显示短日/长日微标提示。
- **依赖与安全边界**：
  纯只读展示，数据取自 `snapshot.timezone`，不增加任何额外查询。
- **验收标准**：
  前端用量工具栏清晰展示当前查询所使用的 IANA 时区名称与当前偏移量，切换系统时区后刷新展示同步变化。
- **优先级 / 工作量 / 额度依赖**：可选 | 工作量 S | 独立无依赖
- **问题属性**：合理优化

## 4. 未验证界限

根据本项目的静态审查与离线验证原则，以下内容明确列为未验证界限，不能将本报告的静态分析推论误判为已经过真机破坏性验证的事实：

1. **真实 Windows NSIS 安装/卸载/升级交互**：
   本审查仅审计了 `src-tauri/windows/installer-hooks.nsh` 与打包脚本，未在一次性干净的 Windows 物理机中反复执行真实的 NSIS 覆盖升级与注册表清理。
2. **多显示器混合 DPI 与极端缩放恢复**：
   窗口尺寸记忆在当前机器实测通过，并在纯模型中覆盖了 6 项边界，但跨多块不同 DPI 显示器热插拔的极端边界未完全覆盖。
3. **真实 Claude 网站 Cloudflare 极端质询行为**：
   网络连通性诊断对 `cf-mitigated: challenge` 头的识别来自 HTTP 模拟规则，真实网络极端风控下的动态质询未做实时逆向测试。
4. **外部包管理器（WinGet/Homebrew/NPM）全局权限变动**：
   CLI 维护更新脚本在受限权限目录下的极端报错恢复，依赖于宿主当前环境变量，未进行破坏性权限模拟测试。
